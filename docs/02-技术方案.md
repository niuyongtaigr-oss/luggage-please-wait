# 行李箱请等等 · 技术方案

> 回答三个问题：用什么语言、用什么架构、为什么这么选。
> 结论先说：**Demo 阶段没有后端，这是刻意的技术决策，不是偷懒。**

---

## 0. 一句话

**零依赖单页应用 + 静态托管。** 一个 HTML、一个 JS，双击就跑，断网可用，GitHub Pages 三十秒上线。

后端不缺席，但**不在 Demo 里**——它的设计已经完成（见 §6），作为「可落地性」写进 Spec，而不是作为「今天要跑通的东西」。

---

## 1. 技术选型

### 前端

| 层 | 选型 | 版本 | 理由 |
|---|---|---|---|
| 标记 | 原生 HTML5 | — | 无构建步骤 = 无构建失败 |
| 样式 | 原生 CSS（CSS 变量 + Grid + clip-path） | — | 一个文件搞定，不用预处理器 |
| 逻辑 | 原生 ES2017+，**无框架、无打包** | — | `file://` 双击即跑 |
| 数据 | `data.js` 挂 `window.DATA` | — | 见下方「为什么不是 JSON」 |
| 路由 | `location.hash` | — | 见下方「为什么不是 history API」 |
| 动画 | CSS `@keyframes` + `requestAnimationFrame` | — | 盖章/撕票/传送带全部纯 CSS |

### 部署

| 项 | 选型 |
|---|---|
| 托管 | GitHub Pages（main / root） |
| 构建 | 无 |
| CDN | GitHub 自带 |
| 域名 | `niuyongtaigr-oss.github.io/luggage-please-wait` |

### 被否决的方案

| 方案 | 为什么不用 |
|---|---|
| React / Vue | 要 `node_modules`、要构建、构建挂了就全挂。2 小时窗口里这是纯风险，零收益 |
| TypeScript | 同上，要编译 |
| Tailwind CLI | 要构建，且 CDN 版要联网 |
| 独立 `.json` + `fetch` | **`file://` 协议下 fetch 会被 CORS 拦死**，断网双击就废了 |
| ES Module (`import`) | 同上，`file://` 下模块加载被拦 |
| history API 路由 | `file://` 下 `pushState` 到 `/review` 会 404 |
| localStorage 存状态 | 排练时残留状态会毁掉现场演示，不如内存干净 |

**两条关键决策值得单独说：**

> **为什么 `data.js` 而不是 `data.json`？**
> `fetch('./data.json')` 在 `file://` 下必然失败（CORS），而 `<script src="data.js">` 永远能加载。
> 用 `window.DATA = {...}` 挂全局，既满足「断网双击就跑」，又满足「两人分文件不打架」。
> 代价：数据不是纯 JSON，但换来的是现场不会因为一个 fetch 报错而白屏。

> **为什么锁死演示数据？**
> 不锁定的话，同场景随机匹配会让你每次排练都抽到不同的卡片，走位背不下来。
> 默认锁第 3 条，`?live=1` 才走真实匹配。**可预测性在路演里比「智能」值钱。**

## 2. 架构总览

```
┌─────────────────────────────────────────────────────────┐
│  index.html  （结构 + 样式 + 全部交互逻辑）              │
│                                                          │
│   ┌──────────────────────────────────────────────┐      │
│   │  视图层  <section class="screen" id="s-*">    │      │
│   │  apply / review / verdict / swap  —— 四屏     │      │
│   └───────────────▲──────────────────────────────┘      │
│                   │  只由 S 驱动（单向）                 │
│   ┌───────────────┴──────────────────────────────┐      │
│   │  状态层  const S = { screen, scene, ... }     │      │
│   └───────────────▲──────────────────────────────┘      │
│                   │  事件只改 S                          │
│   ┌───────────────┴──────────────────────────────┐      │
│   │  事件层  click / input / keydown              │      │
│   └──────────────────────────────────────────────┘      │
│                                                          │
│   工具层：go() 路由 · countTo() 计数 · guardHit() 护栏    │
└────────────────────────┬────────────────────────────────┘
                         │  <script src="data.js">
┌────────────────────────▼────────────────────────────────┐
│  data.js  window.DATA = { meta, applications,            │
│                           verdict, routes, guard }       │
│  纯数据，零逻辑。伙伴独占维护。                          │
└─────────────────────────────────────────────────────────┘
```

**没有框架，但手写了框架的纪律：单向数据流。**
事件 → 改 `S` → `go()`/渲染函数读 `S` 更新 DOM。全站只有一个真相源，没有 DOM 反查状态的地方。

### 状态机

```
        [apply]
           │ submitApply()  ① 校验 → ② 幕布动画
           ▼
      (curtain 2.0s)
           │ enterReview()
           ▼
        [review] ── identity 必选 ──> vote 解锁
           │                          │ vote → reason 解锁
           │ vote + reason + 盖章 1.6s │
           ▼
       [verdict] ── btnToSwap ──> [swap]
                                    │ btnContribute → 小路面板
                                    └ btnReset → [apply]
```

每次状态迁移只做一件事，且**前一步没完成，后一步的 DOM 不存在**（`hidden`），从结构上杜绝跳步。

### 关键模块职责

| 函数 | 职责 | 设计要点 |
|---|---|---|
| `go(name)` | 切屏、更新 GATE 编号、进度条、hash | 唯一改屏入口 |
| `pickApplication()` | 选一份待审申请 | 演示锁死 / `?live=1` 真实匹配 |
| `syncVoteBtn()` | 根据 `S` 派生按钮文案和 disabled | **派生，不存状态**，避免状态不一致 |
| `guardHit(text)` | 纯函数，返回命中的类别和词 | 无副作用，可单测 |
| `renderVerdict()` | 填充判决书 + 计数 + 池子可视化 | 从 `data.js` 读数字，不写死 |
| `countTo(el,t)` | 数字滚动 | **rAF 兜底**：切后台被节流时 `setTimeout` 补终值 |
| `renderCard(i)` | 渲染路线卡 | 支持 `thingHtml` 做显式断行 |

## 3. 数据契约

```js
window.DATA = {
  meta: {
    poolSize: 47,      // 今天池子里有几份
    reviewed: 41,      // 这一轮几个人看了我的
    think: 27,         // 其中几个说再想想
    reviewNo: 12,      // 我现在审的是第几份
    demoIndex: 2,      // 演示固定取第 3 条
    roundLabel: "上一轮 · 2026-10-22 23:40",
    today: "2026.10.22"
  },

  applications: [
    { scene, leaving, ifNot, avoid }   // × 7
  ],

  verdict: {
    quotes: [ { tone, by, text } ]     // × 3：劝走 / 劝留 / 给小路
  },

  routes: [
    { mood, name, dist, thing, thingHtml?, verified, worth, source }  // × 3
  ],

  guard: {
    hint: "这句话可能有点重，要不要再读一遍？",
    note: "AI 护栏 · 本地词库 · 不拦截",
    words: { "羞辱":[...], "说教":[...], "嘲讽":[...] }   // 共 ~40
  }
};
```

**三条契约（写进 Spec 当硬约束）：**

1. `data.js` **不含任何逻辑**——没有函数、没有计算、没有条件。
2. **所有数字只出现在 `meta` 里**，`index.html` 中不出现 `47`/`41`/`27` 字面量。
3. 任何数组长度可变，代码不依赖长度（加第 8 条申请、第 4 张卡，不改一行逻辑）。

## 6. 如果要落地：后端设计

> 这一节**不上线**，写进 `design.md` 用来回答「这东西怎么真正跑起来」。
> 但它不是画饼——表结构和接口是真的能照着写的。

### 6.1 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | **Node 20 + Hono** 或 **Cloudflare Workers** | 边缘部署、冷启动 0ms、免费额度够 |
| 数据库 | **SQLite（Turso / libSQL）** | 单文件、可边缘复制；这个产品的数据量一辈子用不满 |
| 部署 | Cloudflare Workers / Fly.io | 和 Workers 同源，免运维 |
| 客户端 | 复用现有四页，把 `data.js` 换成 API 调用 | 不改架构，只换数据源 |

**为什么不用 Postgres + 常规服务器**：这个产品的高峰就是路演那 3 分钟，没有并发压力，SQLite 足够了。上大件是给评委看的，不是给产品用的。

### 6.2 表结构

```sql
-- 申请
CREATE TABLE applications (
  id          TEXT PRIMARY KEY,      -- nanoid
  scene       TEXT NOT NULL,         -- 旅行/求学/出差/租房/说不清
  leaving     TEXT NOT NULL,
  if_not      TEXT NOT NULL,
  avoid       TEXT NOT NULL,
  created_at  INTEGER NOT NULL,      -- unix ms
  expires_at  INTEGER NOT NULL       -- created_at + 24h
);

-- 陌生人说的话
CREATE TABLE reasons (
  id             TEXT PRIMARY KEY,
  application_id TEXT NOT NULL REFERENCES applications(id),
  identity       TEXT NOT NULL,      -- 过来人/你的身体/你的钱包
  vote           TEXT NOT NULL,      -- go / think
  body           TEXT NOT NULL,      -- ≤60 字，人写的，永不改写
  helpful_count  INTEGER DEFAULT 0,
  created_at     INTEGER NOT NULL
);

-- 小路 / 路线卡
CREATE TABLE routes (
  id        TEXT PRIMARY KEY,
  mood      TEXT NOT NULL,
  name      TEXT NOT NULL,
  dist      TEXT,
  thing     TEXT NOT NULL,
  verified  INTEGER DEFAULT 0,
  worth     INTEGER DEFAULT 0,
  source    TEXT
);

CREATE INDEX idx_app_scene   ON applications(scene, expires_at);
CREATE INDEX idx_reason_app  ON reasons(application_id, vote);
```

### 6.3 接口

| 方法 | 路径 | 作用 | 说明 |
|---|---|---|---|
| `POST` | `/api/applications` | 交申请 | 返回 `{ id, no }`，`no` = 今日第几份 |
| `GET` | `/api/applications/next?scene=` | 取一份待审的 | 同场景优先，24h 内，排除已审 |
| `POST` | `/api/reasons` | 交理由 + 投票 | 服务端**只落库、不解析、不改写** |
| `GET` | `/api/applications/:id/verdict` | 取判决 | 返回计数 + 三类各一句 |
| `POST` | `/api/routes` | 交一条小路 | 三格 |

**取下一份的 SQL（匹配规则写死在数据库层，不交给模型）：**

```sql
SELECT * FROM applications
WHERE expires_at > :now
  AND id NOT IN (SELECT application_id FROM seen WHERE user_id = :uid)
ORDER BY (scene = :scene) DESC, RANDOM()
LIMIT 1;
```

### 6.4 判决书的三类声音怎么来

不是「最高赞一句」，也不是「模型生成」：

```sql
-- 每类取 helpful_count 最高的一条
SELECT * FROM reasons
WHERE application_id = :id AND vote = 'go'
ORDER BY helpful_count DESC LIMIT 1;

SELECT * FROM reasons
WHERE application_id = :id AND vote = 'think'
ORDER BY helpful_count DESC LIMIT 1;

SELECT * FROM routes  -- 给小路：从路线池按情绪抽
ORDER BY RANDOM() LIMIT 1;
```

**这是「AI 不写字」在架构上的落实：判决书里的每一个字都是人写的，数据库只负责排序和归类。**

### 6.5 护栏在哪一层

**在客户端。** 理由正文提交前在浏览器里做本地词库匹配，命中就提示。

服务端收到 POST 时**不做任何内容分析**——不落词库、不打标签、不喂模型。
好处有三：隐私可讲、延迟为零、断网也能demo。

## 6.6 身份：怎么区分「不同的人」和「同一个人」

> 这是整个产品最容易被评委问住的地方，也是我在原型里故意留空的地方。
> **Demo 里的 41 / 27 / 47 是 `data.js` 里的常数，没有任何身份判定。** 见 §6.7 的说明。

### 需求拆解：其实要判断三件事，严格度完全不同

| 要判断的 | 用来做什么 | 严格度 | 不达标会怎样 |
|---|---|---|---|
| **不是自己** | 不能给自己投票 | **高** | 产品直接失去意义 |
| **不同的人** | 「41 个人看了」要诚实 | 中 | 数字虚高，被问穿 |
| **同一个人** | 「你已经审过这份了」、回来看自己的判决 | 低 | 体验瑕疵，不影响成立 |

注意：**「不同的人」和「同一个人」其实是同一个问题的两面**——你只要有一个稳定的伪匿名 ID，两件事同时解决。

### 方案：伪匿名设备 ID（不是账号，不需要登录）

```sql
-- 不是"用户表"，是"设备表"。不进手机号、不进微信、不进任何 PII
CREATE TABLE devices (
  id         TEXT PRIMARY KEY,   -- 首访生成的 nanoid
  first_seen INTEGER NOT NULL,
  last_seen  INTEGER NOT NULL
);

ALTER TABLE applications ADD COLUMN owner_device TEXT NOT NULL REFERENCES devices(id);
ALTER TABLE reasons      ADD COLUMN reviewer_device TEXT NOT NULL REFERENCES devices(id);

-- 核心约束：一个人对一份申请只能有一句
CREATE UNIQUE INDEX uniq_reason_once ON reasons(application_id, reviewer_device);
```

**ID 怎么发：**

1. 首次访问，服务端下发一个 HttpOnly Cookie（`lug_id`）+ 同时在 `localStorage` 写一份。
2. 两者任一还在，就还是同一个人。清缓存只清一边，计数不会重复。
3. 前端**从不读取**这个 ID，随请求自动带上——理由正文和 ID 不同源，隐私上是干净的。

**三条判定规则（全部在数据库层，不在前端）：**

```sql
-- ① 不能审自己
WHERE applications.owner_device <> :me

-- ② 不能重复审同一份（靠唯一索引，不靠前端 if）
INSERT INTO reasons (...) -- 命中 uniq_reason_once 就返回 409

-- ③ 「41 个人」= 去重后的设备数，不是浏览数
SELECT COUNT(DISTINCT reviewer_device)
FROM reasons WHERE application_id = :id;
```

### 数据模型的关键：判决属于「申请」，不属于「人」

```
applications.id ──┬─> reasons (多条，每条来自不同 device)
                  └─> verdict（由 reasons 聚合，不是算出来的新东西）
```

所以「同一个人回来看自己的判决」= 用自己的 `device_id` 查 `applications.owner_device` 匹配的记录。不需要账号，不需要密码。

### 一个现场必踩的坑：WiFi

> **路演现场所有人连同一个 WiFi，出口 IP 是同一个。**

所以：
- **IP 绝对不能用来计数**（否则 47 个人会被算成 1 个人）
- IP 只能用来「防刷兜底」，且阈值要放得很宽
- 任何基于 IP 的去重设计，在这种场景下会当场把自己玩死

### 能被绕过吗？能。为什么不防？

| 绕过方式 | 后果 | 我们的态度 |
|---|---|---|
| 清 cookie + localStorage | 变成"新的人"，可重复投票 | 接受 |
| 隐身窗口 | 同上 | 接受 |
| 换设备 | 同上 | 接受 |
| 脚本刷票 | 数量级远超产品体量，不现实 | 不防 |

**理由：这个产品的敌人从来不是刷票团伙，是「没人愿意当审批人」。**
身份系统的目标是**防止无意的重复**（误清缓存、刷新页面），不是**防止有意的作弊**。
一旦为了防作弊引入登录，产品就死了——没有人会为了给陌生人写一句话去注册账号。

真被问到「怎么防止一个人刷 41 票」，标准回答是：

> 「我们不防。数据库层保证一个人对一份申请只能投一次；真要刷，他可以换 41 台设备。
> 但那 41 句里只要有一句是真的，这个产品就成了。
> 防到需要登录的程度，代价是把 90% 的人挡在门外——那才是真的失败。」

### 还有一条产品规则，比技术更重要

**「以审换审」本身就是最强的身份约束。**

```
你想看自己的判决 → 必须先审一份别人的
想再抽一条小路 → 也要先审
```

这条规则让「同一个人」这个概念在业务上变得必要：系统必须记得你审过了没有。
它同时解决了冷启动、审批人供给、和「凭什么给你审」。

### 落地优先级

| 优先 | 做什么 | 成本 |
|---|---|---|
| P0 | `devices` 表 + 双写 cookie + 唯一索引 | 半天 |
| P1 | 「不能审自己」约束 | 1 小时 |
| P2 | 「审满 N 份才解锁自己的判决」 | 半天 |
| 不做 | 登录、手机号、实名、人机验证 | — |

## 6.7 Demo 阶段为什么不做身份

必须明说：**现在的四页原型里，没有任何身份判定。**

- `41 / 27 / 47 / 12` 全是 `data.js` 里的常数
- 同一个人可以无限次「审」同一份演示数据
- 直接访问 `#verdict` 也能看到判决书

**这是刻意的**：

1. 3 分钟演示里，任何身份相关的分支（重复投票、会话过期、未登录）都是失败点，不是展示点。
2. 评委看的是「这个产品成立吗」，不是「这个 Demo 的账号体系完整吗」。
3. 身份模型写在 `design.md` 里，比塞进 Demo 更有说服力——**说明你想过，而且知道 Demo 该省什么。**

被问到时的标准说法：

> 「演示用预置数据，保证可预测。真实版本按匿名设备 ID 去重，一个人对一份申请只能投一次，判决书按申请聚合——这套模型写在 design.md 里，今天没上线，因为没有必要。」

## 7. 工程约束（写进 `design.md`）

1. **审批理由只能由人输入**，代码中不存在对理由正文的模型调用。
2. **AI 只做护栏**，命中词库仅提示，不拦截、不排序、不评分。
3. **匹配规则写死**：同场景优先 → 全池兜底，不交给模型判断，保证演示可预测。
4. **降级约束**：无网络时全部本地数据，运行时不发任何外部请求。

## 8. 风险与技术债

| 风险 | 影响 | 处理 |
|---|---|---|
| 中文字体缺失 | 版面变丑 | 全部用系统字体栈，不下载字体 |
| 投影仪偏色 | 荧光黄变脏绿 | `?proj=1` 提对比；现场先用手机拍一张看色 |
| 内存态丢失 | 刷新回到第一页 | 有 `?static=1` 和 hash 直达，重走一遍 40 秒 |
| 双人同时改一个文件 | 冲突 | 已按文件独占拆分（`index.html` / `data.js`） |
| 无自动化测试 | 改坏不自知 | 有固定 e2e 走位脚本（见 `03-任务拆分.md`） |

**已知技术债（不上线就不还）：**
