# Design · 行李箱请等等

> Spec-driven development · 设计阶段
> 版本 1.0 · 2026-10-22
> 本文档只记录**决策**和**为什么**，不重复需求。

---

## 1. 设计目标

在**两小时**内，做出一个**断网可用、双击即跑、现场零翻车**的四页 Demo，同时保留一条通往真实产品的技术路径。

这两个目标互相拉扯：真实产品需要后端、身份、去重；而现场演示最怕的恰恰是网络和后端。

**全篇的设计都围绕这个张力展开。**

---

## 2. 三条硬约束

这三条不是「尽量」，是**不可协商**。任何实现冲突时，以这三条为准。

### C-1 审批理由只能由人输入

**约束：** 代码中不存在对理由正文的任何模型调用、改写、纠错、润色。

**验收方式：** 全文搜索理由提交路径，从 `#fReason` 的 value 到数据库 `reasons.body`，中间不得经过任何生成式调用。

**为什么：** 陌生人写的那句话是这个产品唯一不可替代的东西。一旦模型参与，产品就退化成「AI 给你建议」，而市面上已经有十万个了。

### C-2 AI 只做护栏，不做作者

**约束：** 命中词库时仅提示，不拦截、不排序、不评分、不改变发送权。

**验收方式：** 词库命中后，提交按钮的 `disabled` 属性必须仍为 `false`。

**为什么：** 这是产品里 AI 唯一的落点。它必须能一句话说清：**「这个产品里，AI 不写字。AI 只在你准备伤人的时候，轻轻碰一下你的手。」**

### C-3 匹配规则写死，不交给判断

**约束：** 同场景优先 → 全池兜底 → 随机；演示模式下锁死第 3 条。

**验收方式：** 同一操作路径重复执行，结果必须一致。

**为什么：** 路演只有一次机会，**可预测性比智能值钱**。

## 3. 系统架构

```
┌──────────────────────────────────────────────────────────┐
│  浏览器                                                   │
│                                                           │
│  ┌─────────────────────────────────────────────────┐     │
│  │ index.html                                      │     │
│  │  视图层   <section class="screen" id="s-*">     │     │
│  │            ▲                                    │     │
│  │  状态层   S = { screen, vote, identity, ... }   │     │
│  │            ▲                                    │     │
│  │  事件层   click / input / keydown               │     │
│  └─────────────────────────────────────────────────┘     │
│         │                    │                            │
│         │ data.js            │ api.js (fetch)              │
│         ▼                    ▼                            │
│    本地演示数据          Supabase REST /rpc/*              │
└──────────────────────────────┼───────────────────────────┘
                               │
                    ┌──────────▼───────────┐
                    │ Supabase (Postgres)  │
                    │ applications         │
                    │ reasons              │
                    │ routes               │
                    │ + 6 个 security      │
                    │   definer 函数       │
                    └──────────────────────┘
```

**数据流是单向的：** 事件 → 改 `S` → `go()` / 渲染函数读 `S` 更新 DOM。没有 DOM 反查状态的地方。

**没有框架，但手写了框架的纪律。** 这是两小时内还能保持可维护的根本原因。

## 4. 双轨数据源（本设计最关键的一个决定）

同一个 `index.html`，两种数据源，**形状完全一致**：

```js
window.DATA = { meta, applications, verdict, routes, guard, empty }
```

| 轨道 | 触发 | 数据来源 | 用途 |
|---|---|---|---|
| **静态轨**（默认） | 无参数 | `data.js` | 3 分钟 pitch，可排练、断网可用 |
| **在线轨** | `?live=1` | Supabase | 评委扫码真玩，池子真涨 |

### 降级是一等公民

```js
async function loadData(){
  if(!LIVE_OK) return window.DATA;
  try{
    const r = await fetch(URL, { signal: AbortSignal.timeout(1500) });
    return await r.json();
  }catch(e){
    goOffline();          // 角标切成「离线 · 演示数据」
    return window.DATA;   // 演示不中断
  }
}
```

**任何一次 API 失败立刻回落，不卡在中间状态。**

### 为什么不用 supabase-js

官方 SDK 要从 CDN 加载。**现场多一个 CDN 就多一个失败面。**

改用手写 `fetch` + 6 个 RPC：零依赖、零 CDN、断网双击也能跑。

代价：放弃 Supabase 的匿名登录和类型提示。可接受——我们本来就不需要「用户」这个概念。

## 5. 身份模型

### 5.1 要判断三件事，严格度完全不同

| 要判断的 | 用途 | 严格度 |
|---|---|---|
| 不是自己 | 不能给自己投票 | **高** |
| 不同的人 | 「41 个人看了」要诚实 | 中 |
| 同一个人 | 「你已经审过这份了」 | 低 |

**「不同的人」和「同一个人」是同一个问题的两面**——一个稳定的伪匿名 ID 同时解决两者。

### 5.2 实现

```
device_id = 首次访问时 localStorage 生成一个 UUID
```

**不是账号，是「这台设备这一轮」的标识。** 不收集任何 PII。

数据库层三道闸：

```sql
-- 闸 1：一个人对一份申请只能有一句
unique (application_id, device_id)

-- 闸 2：不能审自己
where a.device_id <> p_device

-- 闸 3：人数是去重值，不是条数
count(distinct device_id)
```

### 5.3 明确不做

**不做防作弊。**

| 绕过方式 | 态度 |
|---|---|
| 清 localStorage | 接受，变成新的人 |
| 隐身窗口 | 接受 |
| 换设备 | 接受 |

**理由：** 这个产品的敌人不是刷票团伙，是「没人愿意当审批人」。为防作弊引入登录，等于把 90% 的人挡在门外。

被问到时的回答：

> 「我们不防。数据库保证一个人对一份申请只能投一次；真要刷，他可以换 41 台设备。但那 41 句里只要有一句是真的，这个产品就成了。」

### 5.4 一个必须写进文档的坑

**同一 WiFi 下所有人共用出口 IP。** 因此 IP 只能用于宽松的防刷兜底，**绝不能用于计数或去重**——否则 47 个人会被算成 1 个人。

## 6. 轮次模型

### 6.1 一轮 = 一个自然日（Asia/Shanghai）

```
poolSize       = 今天 00:00 之后提交的份数
「今天第 N 份」 = 今天第几个交的
审批页抽到      = 只从今天的池子里抽
判决书          = 不按日期过滤（昨天的申请今天被读完，就该回来找你）
```

**「上一轮」不是文案修辞，是数据结构。**

### 6.2 为什么不能用 `current_date`

`current_date` 使用数据库会话时区，Supabase 默认 **UTC**。

上海时间 0:00–8:00 这段时间，UTC 还是昨天——**凌晨 1 点交的申请会被算进前一天**。

统一改用：

```sql
create function round_start() returns timestamptz as $$
  select date_trunc('day', now() at time zone 'Asia/Shanghai')
         at time zone 'Asia/Shanghai';
$$;
```

**验证记录：** 插入一条 `created_at = now() - interval '1 day'` 的申请后，
`poolSize` 保持 4 不变，连续抽 20 次未命中该条。轮次边界成立。

### 6.3 数据只增不删

清库是**可选的**演示前卫生动作，不是结构要求。昨天的数据今天自动不在池子里。

## 7. 安全模型

| 项 | 做法 | 理由 |
|---|---|---|
| 表权限 | `revoke all on tables from anon` | 前端只该调 RPC，不该碰表 |
| 读写入口 | 6 个 `security definer` 函数 | 唯一入口，逻辑集中 |
| RLS | 三张表全开，不建任何 policy | 默认拒绝 |
| 密钥 | 只用 `sb_publishable_`（可公开） | `service_role` 绝不进前端 |
| 数据外发 | 静态轨零请求；在线轨只发业务字段 | 隐私可讲 |

**已验证：** 用 anon 密钥直接 `GET /rest/v1/applications` 返回 `42501 permission denied`。

## 8. 前端状态机

```
        [apply]
           │ submitApply()  校验 → 写入 → 幕布
           ▼
      (curtain 2.0s)
           │ enterReview()
           ▼
        [review] ── identity 必选 ──> vote 解锁
           │                          │ vote → reason 解锁
           │                          │ think → 追加格出现
           │ vote + reason + 盖章 1.6s │
           ▼
       [verdict] ── btnToSwap ──> [swap]
                                    │ btnContribute → 小路面板
                                    └ btnReset → [apply]
```

**渐进披露的硬性顺序：** 身份 → 投票 → 理由 → 提交 → 盖章。
前一步没完成，后一步的 DOM 不存在（`hidden`），**从结构上杜绝跳步**。

## 9. 数据契约

```js
window.DATA = {
  meta:        { poolSize, reviewed, think, reviewNo, demoIndex, roundLabel, today },
  applications:[ { scene, leaving, ifNot, avoid } ],          // × 7
  verdict:     { quotes: [ { tone, by, text, helpful } ] },   // × 3
  routes:      [ { mood, name, dist, thing, verified, worth, source } ],  // × 3
  guard:       { hint, note, words: { 羞辱, 说教, 嘲讽 } },   // ~40 条
  empty:       { hudZero, sealZero, subZero, capEmpty, ... }
};
```

**三条契约：**

1. `data.js` 不含任何逻辑——没有函数、没有计算、没有条件。
2. 所有数字只出现在 `meta`，`index.html` 中**不出现任何业务数字字面量**。
3. 任何数组长度可变，代码不依赖长度。

**所有数字的唯一出口是 `hydrate()`**，它同时负责空状态文案。

## 10. 可预测性设计

| 手段 | 作用 |
|---|---|
| `?static=1` | 关闭全部动画，用于截图与救场 |
| `?proj=1` | 配色不变，抬对比加粗线，用于劣质投影 |
| `Ctrl/⌘ + K` | 一键填表，**全程不打中文** |
| `#review` / `#verdict` / `#swap` | 直达某页，排练用 |
| 演示锁死第 3 条申请 | 每次排练抽到同一张卡 |
| `data.js` 缺失兜底 | 不白屏，提示缺哪个文件 |

## 11. 技术选型与被否决方案

| 层 | 选型 | 被否决 | 否决理由 |
|---|---|---|---|
| 标记 | 原生 HTML | React/Vue | 要构建，构建挂了全挂 |
| 逻辑 | 原生 ES2017+ | TypeScript | 要编译 |
| 样式 | 原生 CSS | Tailwind CDN | 要联网 |
| 数据 | `data.js` 挂全局 | `data.json` + fetch | **`file://` 下 fetch 被 CORS 拦死** |
| 路由 | `location.hash` | history API | `file://` 下 404 |
| 后端 SDK | 手写 fetch | supabase-js | CDN 是新的失败面 |
| 状态持久化 | 无（内存） | localStorage | 排练残留会毁掉现场演示 |

## 12. 已知取舍

| 取舍 | 我们选了什么 | 放弃了什么 |
|---|---|---|
| 可预测 vs 智能匹配 | 锁死第 3 条 | 真实感 |
| 零依赖 vs 开发效率 | 原生 + 手写 fetch | 框架生态 |
| 隐私 vs 防作弊 | 只防误重复 | 防恶意刷票 |
| 好看 vs 可信 | 空库说人话 | 永远好看的数字 |
| 一屏可见 vs 内容完整 | 双栏紧凑 | 大留白 |

**最后一条值得展开：** 空库时显示「今天刚开始」而不是「47」，短期内不好看，但它保证了「41 个人」这个数字在被追问时站得住。**这是这个产品唯一真正值钱的地方。**

## 13. 风险

| 风险 | 概率 | 处理 |
|---|---|---|
| 投影仪偏色 | 中 | `?proj=1`；到场先用手机拍一张 |
| 现场网络断 | 中 | 静态轨零请求；在线轨 1.5 秒超时回落 |
| 中文字体缺失 | 低 | 全系统字体栈，不下载字体 |
| 输入法打中文卡壳 | 高 | `Ctrl+K` 预填，全程不碰键盘输入 |
| 评委问「41 个人哪来的」 | 高 | 页脚「上一轮」+ 身份模型文档 |
| 评委问「产品里 AI 在哪」 | 高 | 现场演一次护栏 + 金句 |
